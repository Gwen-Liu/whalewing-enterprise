# 鲸翼企业版第一版设计

> 状态：第一版（`0.2.1-rc.5.1`）按本文实现，2026-11-01 发布到 GitHub、2026-11-02 发到 npm（预发布）；当前开发版本 `0.2.1-rc.5.2`。本文写的是现在采用的做法；和最初设计稿不一样的地方都已改成实际做法，见文末“和设计稿的出入”。
>
> 下一块“企业管理”（事项、组织和权限、看板、填报）的设计在[企业管理设计](企业管理设计.md)，2026-11-02 定稿；第二版（角色和权限、事项和项目、我的工作、团队看板、`team_work`）和助手改名（企业把“小鲸助手”改成自己的叫法）已在开发版本里实现，还没发布。**第二版起没有“所有者”了**：管理员可以有多个、互相平级，成员挂自定义角色，见企业管理设计。下面“角色”一条写的是第一版的做法。

## 一句话

让一家企业把**团队知识、团队专家、团队技能**集中维护、按部门和人分配，员工在自己的鲸翼里直接用，鲸翼个人版原来的功能一样不少。

## 第一版做什么、不做什么

| 做 | 不做（以后再说） |
| --- | --- |
| 服务端：账号、部门层级、邀请、团队知识、团队专家、团队技能、可见范围和维护人、管理操作记录 | 管“员工能用哪些功能和模型”（2026-11-02 取消，以后也不做：模型和功能由员工自己选） |
| 管理端网页：初始化向导、成员与部门、邀请、三类团队内容、企业设置、操作记录 | 接企业已有账号（OIDC、企业微信、钉钉、飞书） |
| 员工端组合包：加入企业、登录、「团队」页签、团队内容接进鲸翼原来的页面、维护人在鲸翼里改团队内容、提交个人笔记、退出时撤掉团队内容 | 普通成员提交、维护人审核的流程；第一版只有维护人能改 |
| 鲸翼个人版开的两处通用插槽（专家来源、知识来源）和技能库的“扩展”分组 | 一个工作台同时连多家企业 |
| npm、Docker、源码三种装法 | 自带运行环境的离线安装包；托管版；员工会话审计 |

## 整体结构

```
员工电脑上的 DSH                                      企业自己的服务器
┌────────────────────────────────────┐            ┌──────────────────────────────┐
│ 鲸翼个人版 dsh-whalewing             │            │ whalewing-enterprise-server  │
│   专家团队 ← 专家来源插槽 ─┐          │            │   员工端接口 /api/v1          │
│   个人知识 ← 知识来源插槽 ─┤          │   HTTPS    │   管理端网页 /admin/          │
│   技能库   ← 扩展技能目录 ─┤          │ ◄────────► │   数据目录 data/              │
│                          │          │（内网可 HTTP）│     SQLite：账号、权限、记录   │
│ 鲸翼企业版 dsh-whalewing-enterprise  │            │     content/：知识、专家、技能  │
│   「团队」页签、连接与同步、本机缓存     │            └──────────────────────────────┘
└────────────────────────────────────┘
```

- 模型不经过服务端；服务端不保管模型 Key。
- 员工的个人知识、个人技能、会话从不上传；只有员工点“提交到团队”的那一篇才发给服务端。
- 权限在服务端判断；员工端的只读、可改只是显示。

## 团队内容和权限

| 内容 | 格式 | 组织 |
| --- | --- | --- |
| 团队知识 | Markdown，和个人知识同样的格式 | 按知识空间分，空间里可以有子目录；只放 `.md` |
| 团队专家 | 专家模板文件 `expert.md`，和个人版的专家模板同一种格式（开头 name、description、skills、avatar，正文是提示词） | 平铺列表 |
| 团队技能 | 技能目录，根目录有 `SKILL.md`（开头 `name` 要和技能标识一样，还要有 `description`），和 DSH 同一种格式 | 平铺列表 |

- 每项内容有一个**标识**：小写字母、数字和夹在中间的单个短横线，最长 64；团队专家和技能直接拿它当 id 和技能名。
- **角色**：所有者（初始化时建的第一个管理员，不能停用、不能改角色）、管理员、成员。只有所有者能设置、停用、邀请管理员，能重置管理员的密码。
- **部门**是一棵树，每个成员属于一个部门。
- 每项内容有**可见范围**（全员 / 指定部门，自动包含下级部门 / 指定成员）和**维护人**（指定部门或成员）。维护人自动能看。新建默认“全员可见、只有管理员能改”。新建、删除内容项和改权限只在管理端做。
- 看不到的内容一律回“不存在”，不让人从报错里猜出有哪些内容。
- **防覆盖**：保存时带上读到的那一版的指纹，对不上就拒收，提示重新读取；同一项内容的写入在服务端排队，两个人同时保存只有一个成功。
- Windows 上只差大小写的文件会撞名，服务端拒收这类路径，也拒收 `..`、隐藏文件和 Windows 不允许的文件名。

## 员工端

### 「团队」页签

| 状态 | 显示 |
| --- | --- |
| 没有连接 | 一个输入框：邀请链接或服务器地址 |
| 已连接 | 我的信息（企业、部门、身份、服务器、是否加密）和“退出团队”；知识空间、团队专家、团队技能三组卡片；维护人能新建、修改笔记，提交个人笔记，修改技能的 `SKILL.md` |
| 连不上 | 缓存的内容照常能用，说明原因和上次同步时间 |
| 登录失效（过期、被停用） | 团队内容已撤掉，说明原因，可以重新登录 |

页头“…”里的“刷新”就是立即同步。交互和颜色全部用鲸翼工作台公开的组件和 DSH 变量，跟随皮肤。

### 连接和登录

- **邀请链接**形如 `https://服务器地址/join/<邀请码>`；员工端从里面取出服务器地址和邀请码。浏览器直接打开这条链接会看到一页说明。
- **先确认再连**：先请求服务器的公开信息，弹窗显示“你将加入：××公司”、服务器地址、是否加密；邀请还显示加入的部门和身份。原因：团队专家和技能会让模型在员工电脑上读写文件、执行命令，连谁就等于信任谁。
- **加密规则**：外网地址只能 https，证书不被信任时说明原因，不提供“忽略继续”；地址（填域名时看解析出来的地址）在内网网段才允许 http，并标明没加密。请求不跟随跳转，免得令牌被带到别的服务器。
- **令牌**存在 DSH 的凭据存储里，按 DSH profile 分开；30 天不用过期；管理员停用账号、改角色、重置密码时立刻作废。
- **接口版本**对不上时，提示该升级服务端还是员工端。
- 一个工作台只连一家企业；要换先退出。

### 同步和本机缓存

- 启动时、每 10 分钟、点刷新时同步。服务端返回这个人能看的全部内容和每个文件的指纹（带 ETag，没变化时只回 304），员工端只下载指纹对不上的文件，下载后再核对指纹；清单里没有的就删掉，所以改了可见范围、换了部门，下次同步就撤掉。
- 缓存放在当前 DSH profile 目录下的 `whalewing-enterprise/`，和个人知识库、`~/.dsh/skills` 分开。服务端发来的路径会先按同样的规则校验，写不到缓存目录外面。
- **离线**：连不上时缓存照常用；超过企业设置的天数（默认 7 天）还连不上就先撤掉，连上后自动恢复。
- **退出、停用、过期**：本机的令牌和团队内容删掉，鲸翼里的团队专家、团队知识、团队技能跟着撤下；个人内容不动。

### 接进鲸翼个人版

按个人版公开的扩展接口（个人版 `EXTENDING.md`）接入，不改个人版源码、不导入个人版内部文件：

| 团队内容 | 接法 | 员工看到的 |
| --- | --- | --- |
| 团队专家 | `ctx.whalewing.experts.registerSource`，每次同步完把列表推过去 | “专家团队”里标“团队”，排在自己的专家后面；维护人能直接“编辑专家”，保存时写回服务端；其他人能查看、复制为自己的专家。模型和 MCP 跟随员工本机设置 |
| 团队知识 | `ctx.whalewing.knowledge.registerSource`，搜索和阅读都查本机缓存 | 知识搜索、小鲸引用、模型用的知识工具都能搜到，标题写“知识空间 / 笔记标题”，标“团队”；阅读时只读；能引用给小鲸助手（给的是本机缓存文件） |
| 团队技能 | 登记扩展时带一个技能缓存目录，DSH 监听目录变化 | 技能库“扩展 · 团队”一组，只读；专家和小鲸都能调用 |
| 助手名称（企业管理第二版起） | `ctx.whalewing.assistant.registerName`，企业设置里有名字就登记，改名用 `set`，清空、退出时 `dispose` | 鲸翼里的“小鲸助手”换成企业起的名字；编辑小鲸时名字只读，写明由「团队」统一设定。见[企业管理设计](企业管理设计.md#助手改名实现说明2026-11-05) |

## 服务端

| 选什么 | 定为 | 理由 |
| --- | --- | --- |
| 运行环境 | Node.js 24 起 | 和 DSH 桌面版自带的 Node 同一代；员工端和服务端一种语言 |
| Web 框架 | Fastify 5 | 成熟，限流、Cookie 有官方插件 |
| 数据库 | Node 自带的 `node:sqlite` | 不用装数据库，没有原生依赖 |
| 接口定义 | zod 4，写一份放 `shared/` | 两端共用，对不上时在校验那一步拦下 |
| 密码 | Node 自带的 scrypt 加盐哈希 | 不用原生依赖 |
| 管理端 | React + Vite，构建成静态文件由服务端直接提供 | 不用单独部署前端 |

### 数据目录

```
data/
  whalewing-enterprise.db    账号、部门、权限、邀请、令牌（只存指纹）、内容索引、操作记录
  content/knowledge|experts|skills/<标识>/...
  backups/                   结构升级前的自动备份
  server.json                （可选）端口、监听地址、是否在反向代理后面
  setup-code.txt             初始化码，初始化后删除
```

### 接口（`/api/v1`）

| 用途 | 接口 | 谁能用 |
| --- | --- | --- |
| 公开 | `GET /hello`、`GET /invites/<邀请码>`、`POST /setup`（要初始化码，只能一次） | 所有人 |
| 登录 | `POST /auth/login`、`POST /auth/join`、`POST /auth/logout`、`GET /me`、`POST /me/password` | 员工、管理员 |
| 同步 | `GET /sync`（带 ETag） | 员工端，按可见范围过滤 |
| 文件 | `GET`、`PUT`、`DELETE /items/<种类>/<标识>/files/<路径>` | 能看的读；维护人和管理员改 |
| 管理 | `/admin/overview`、`users`、`departments`、`invites`、`items`、`settings`、`audit`（第二版加了 `roles`、`work-types`、`work/trash`、`work/import`） | 管理员（只认管理端 Cookie） |

失败一律返回 `{ error: { code, message } }`，`message` 给人看。

### 安全

- 同一登录名连续输错 5 次锁 15 分钟，同一地址 30 次；所有接口按地址限速；登录名不存在时也算一次哈希，不从快慢猜账号。
- 令牌 32 字节随机数，数据库只存指纹。管理端用 HttpOnly、SameSite=Strict 的 Cookie（https 下带 Secure），会改东西的请求还要带自定义请求头，防跨站提交。员工端令牌不能调管理接口。
- 初始化必须填启动时生成的初始化码。
- 文件内容返回时带 `Content-Security-Policy: sandbox`，浏览器直接打开也不会当网页执行；网页带内容安全策略和不许被嵌入的响应头。
- 技能压缩包检查路径、文件数和解开后的大小，服务端不执行任何上传的内容。
- 操作记录只记管理动作（成员、部门、邀请、内容、设置），不记员工会话，不记密码。

## 版本与发布

- 版本号 = 适配的 DSH 完整版本号 + 企业版自己的序号；服务端、管理端、员工端用同一个版本号、同一个标签。第一版 `0.2.1-rc.5.1`。
- 员工端 `engines.dsh` 写 `0.2.1-rc.5`；第一版需要鲸翼个人版 `0.2.1-rc.5.2` 或更新的 rc.5 版本（第一个带两处插槽的版本）；企业管理第二版起要 `0.2.1-rc.5.4` 或更新（第一个带助手名称接口的版本）。个人版太旧时员工端报错说明要升级个人版。要的个人版版本靠员工端启动时检查接口，不写 `peerDependencies.dsh-whalewing`（个人版扩展接口的版本范围要等它首个封版时定，不预填）。
- 发布两个 npm 包：`dsh-whalewing-enterprise`、`whalewing-enterprise-server`（共用部分打进包里）；Docker 镜像发到 GitHub 镜像仓库，镜像文件放进 Release。

## 和设计稿的出入

1. **同步方式**：设计稿写的是“按修订号只回变化”，实际是每次回这个人能看的完整清单（带文件指纹和 ETag）。原因：可见范围、部门变化时，按修订号很难算准“这个人新增或失去了哪些内容”；完整清单一次比对就准，几千个文件的清单也只有几百 KB，没变化时只回 304。
2. **知识空间名**：个人版搜索结果只显示来源名“团队”，所以把知识空间名放进标题（“研发手册 / 代码评审”）。
3. **团队专家的头像**：个人版的来源专家头像要求是图片数据，专家模板里的是头像标识，第一版团队专家用默认头像；保存时保留模板里原来的头像标识。
4. **专家页不自动刷新**：同步后团队专家变了，已经打开的“专家团队”页要点刷新或重新进入才更新；知识搜索每次都现查。
5. **新建内容项只在管理端**：员工端维护人只能改已有内容（新建笔记、改文件、提交个人笔记），新建知识空间、专家、技能和改权限在管理端做。
6. **管理端改技能**：技能里 `SKILL.md` 以外的文件（脚本、参考资料）只能在管理端上传压缩包整体替换；员工端只改 `SKILL.md`。
