# 鲸翼企业版：企业管理设计

> 状态：**草案**，2026-11-02 写，等维护者审核；审核前不动代码。
> 第一版（见[设计](设计.md)）做了团队知识、团队专家、团队技能。本篇加第三块：**企业管理**——团队每天的工作（事项）、谁管谁（组织和权限）、每个人和每个组做得怎样（看板、日报）。

## 一句话

团队的日常工作放进员工每天用的 DSH 里，从第一天起模型就能读、能改——用员工自己的权限，在员工自己的电脑上跑。

## 为什么放在鲸翼里做

- **工作本来就在 DSH 里发生。** 写代码、写文档、查资料、整理会议记录都在 DSH 里做。事项和进度就放在旁边，模型做事时顺手就能查、能更新，员工不用切到另一个系统手填。
- **在现成系统上加 AI，AI 只看得到被手填进去的那一点。** 填不填、填得准不准全靠人。这里的模型能看到员工当天实际做了什么（只在员工本机，员工确认后才上报），所以日报、进度、风险都能有依据地起草。
- **AI 和人走同一套权限。** 模型通过工具调服务端，服务端按这个人的身份判断，不给模型开后门；人做不了的事，模型也做不了。

## 叫法

- **事项**：团队里要做的一件工作。不叫“任务”，因为 DSH 已经有“定时任务”“后台任务”和给模型用的待办，混在一起分不清。
- **项目**：一组事项属于同一个项目。
- **动态**：事项的变化记录和评论。
- **日报、周报**：员工提交给上级看的工作小结。
- **我的工作**、**团队看板**：员工端「团队」页签里的两个页面。

## 从常见团队管理系统里吸取的教训

下面是这类系统常见的问题，企业管理按右边一列来做：

| 常见问题 | 后果 | 这里怎么做 |
| --- | --- | --- |
| “我的看板”按**创建人**统计，旁边又写着“只显示你负责的” | 普通成员几乎不建事项，看板全是 0，说明文字和数字对不上 | “我的”一律按**负责人**算；创建人只是一条记录 |
| 实施、接口、开发、跟踪各建一张表，字段八成一样，编号、状态叫法、“完成日期”的名字各不相同 | 改一处要改四处；跨类型的统计算不了 | **一种事项 + 类型**。类型只决定编号前缀、状态叫法和少数专属字段 |
| 进度手填，和状态脱节：已完成的事项进度 45%，已关闭的 0% | 平均进度没意义 | 状态归到五个大类；已完成就是 100%，未开始就是 0；有检查项时按检查项算 |
| 权限写在页面说明里（“删除只由某几个账号处理”），其他人都能改所有事项 | 换人就要改代码；谁改了截止日期查不到 | 角色和权限点由管理员配；每次改动进动态，写清谁、何时、从什么改成什么 |
| 只有“我的”，没有“我的团队” | 组长看不到组员做得怎样，只能挨个问 | 团队看板按管理范围汇总，可以一层层点进去 |
| 每一行都显示同一个关联项目；表格十几列，要横向滚动才看得到操作 | 关键信息被挤掉 | 项目放到筛选和页头；列表只留关键几列，其余进详情抽屉 |
| 没数据时画一个空坐标轴 | 看不出是没数据还是坏了 | 没数据时说清为什么没有、下一步做什么 |
| 资料库和事项分开，文档挂不到事项上 | 找资料靠记忆 | 事项直接引用团队知识里的文档 |
| 没有日常节奏：没有“今天要做什么”，没有日报，进度改了没记录 | 管理只剩月底对表 | 我的工作（今天）+ 日报 + 动态 |

## 角色和权限

### 两件事分开：能做什么、能看谁的

- **能做什么**（功能权限）：比如能不能派事项、能不能删除。这是 RBAC（基于角色的权限控制）管的：人 → 角色 → 权限点。
- **能看谁的数据**（数据范围）：比如组长能看自己组员的事项。这叫数据权限或数据范围。

国内的企业系统大多是这两样配合着用。这里也一样：**角色 = 一组权限点 + 一个数据范围**。

### 固定的两个角色

| 能做的事 | 超级管理员 | 管理员 |
| --- | --- | --- |
| 日常业务的全部：事项、项目、看板、日报、组织和人员、角色、事项类型、团队内容、邀请 | ✓ | ✓ |
| 任命、停用管理员和超级管理员，重置他们的密码 | ✓ | ✗ |
| 操作记录 | 全部，含系统日志 | 只看业务记录（人员、事项、内容的变化） |
| 安全设置：登录锁定、令牌有效期、内网是否允许 HTTP | ✓ | ✗ |
| 备份、恢复、导出全部数据 | ✓ | ✗ |
| 彻底删除（清空回收站）、删除整个部门的数据 | ✓ | ✗ |
| 维护模式、数据结构升级 | ✓ | ✗ |

- **超级管理员就是部署和维护服务器的人。** 能登服务器、能直接改数据库的人，不管在系统里是什么角色，实际上都是超级管理员。所以这个角色人要少、操作要留记录。开发和测试部署时，维护者自己就是超级管理员。
- 第一版的“所有者”改名为超级管理员。可以有多个，至少留一个启用的；只有超级管理员能任命超级管理员和管理员。
- 忘记密码、恢复备份这类救急操作走服务器命令行（`whalewing-enterprise-server` 的子命令），要先登上服务器，网页里不提供。
- **管理员是日常使用的最高权限**：调整任何人的事项（截止日期、优先级、负责人）、建组织、配角色，都由管理员做。

### 管理员自己定义的角色

管理员按企业自己的叫法建角色：负责人、小组长、组员、项目经理……都行。每个角色勾一组权限点、选一个数据范围。

**权限点**（故意只有这几个，不做几百个开关）：

| 权限点 | 能做什么 |
| --- | --- |
| 新建事项 | 给自己建事项（默认人人都有） |
| 派事项 | 给范围内的人建事项、改事项的负责人 |
| 调整事项 | 改范围内事项的截止日期、优先级、状态 |
| 删除事项 | 把范围内的事项放进回收站 |
| 看团队看板 | 看范围内的汇总和每个人的事项 |
| 看日报 | 看范围内的人提交的日报和周报 |
| 管项目 | 建项目、管项目成员 |
| 导出 | 把范围内的事项导出成表格 |

管组织和人员、管角色、事项类型、企业设置、从回收站恢复，这些只给管理员，不能分给自定义角色（以后要“负责人管自己部门的人”再加）。

**数据范围**三选一：

| 数据范围 | 意思 |
| --- | --- |
| 仅本人 | 只管自己负责的事项 |
| 管理范围 | 他担任负责人的部门，连同下级部门 |
| 全部 | 全企业，比如管理办公室 |

预置两个角色，管理员可以改名、改权限或删掉：**负责人**（管理范围，除删除外的权限点都勾上）、**成员**（仅本人，只有新建事项）。第一版的“成员”升级后就是这里的成员。

### 上下级从哪来：组织树 + 部门负责人

不给角色排“第几级”。组织是一棵部门树（第一版已经有），每个部门可以设一个或几个**负责人**。一个人担任负责人的那些部门，连同下级部门，就是他的管理范围。

```
公司                      管理员：甲
└─ 交付中心               负责人：乙（角色“负责人”）
   ├─ 一组                负责人：丙（角色“小组长”）   成员：丁、戊
   └─ 二组                负责人：己（角色“小组长”）   成员：庚
```

- 乙的范围是交付中心、一组、二组；丙只有一组；己只有二组。**上级比下级看得多，是树自己带出来的**，不用另外配。两个小组长互相看不到对方的组。
- 负责人和小组长的区别由管理员定：比如负责人能删除事项、小组长不能。
- 一个人可以兼管几个部门（在几个部门都设成负责人）。跨部门的合作用**项目成员**解决，不用改组织树。
- 角色是“管理范围”、但他还不是任何部门的负责人时，实际上只能管自己；管理端会提示。

### “看”和“改”分开

- **改**：自己负责的事项，能更新进度、状态和动态；别人的事项，要在自己的数据范围里，并且有对应的权限点。
- **看**：默认能看到 = 数据范围里的 + 自己参与的（负责、协作、创建、在等我）+ 同项目成员的事项。企业设置里可以改成“全员可见”，适合人少、讲透明的团队。

### 防止越权

- 全部在服务端判断（沿用第一版）；模型调工具也走同一套判断。
- 看不到的事项一律回“不存在”，不让人从报错里猜出有哪些事项。
- 删除先进回收站，管理员能恢复，只有超级管理员能彻底删。
- 改截止日期、优先级、负责人、删除，都记进事项的动态和操作记录：谁、什么时候、从什么改成什么、是本人操作还是经模型操作。

## 事项

### 一种事项，多种类型

| 字段 | 说明 |
| --- | --- |
| 编号 | 自动生成：`类型前缀-年月-序号`，如 `KF-202611-007`；删掉的号不再用 |
| 标题 | 必填 |
| 类型 | 管理员定义，见下 |
| 项目 | 可以不属于任何项目 |
| 负责人 | 只有一个；“我的工作”按它算 |
| 协作人 | 可以多个，能看、能写动态 |
| 创建人 | 自动记 |
| 状态 | 用类型自己的叫法，每个状态归到一个大类 |
| 优先级 | 高、中、低 |
| 开始日期、截止日期 | 截止日期用来算逾期 |
| 完成时间 | 状态进入“已完成”时自动记 |
| 进度 | 见下 |
| 等待 | 在等谁、等什么，一句话 |
| 内容 | Markdown |
| 检查项 | 可选的小清单 |
| 引用资料 | 团队知识里的笔记 |
| 专属字段 | 类型自己的几个字段 |

**类型**由管理员在管理端配：名称、编号前缀、状态列表（每个状态归到哪个大类）、最多 5 个专属字段（单选、文本、日期）。预置“任务”一个类型，管理员照着加“开发”“实施”“跟踪”这类。

**五个状态大类**：未开始、进行中、等待中、已完成、已取消。所有统计都按大类算，所以各类型的状态叫法可以不一样，看板照样能合起来。

### 进度和逾期

- 已完成 = 100%、未开始 = 0%，自动；只有进行中、等待中的事项才填进度。
- 有检查项时进度按检查项完成的比例算，不用手填。
- **逾期** = 截止日期已过，并且大类不是已完成、已取消。等待中的照样算逾期，看板上标出在等谁。

### 等待

任何事项都能标“在等谁、等什么”。被等的人在“我的工作”里看到“等我答复”。

### 动态

每个事项一条时间线：状态和进度的变化、截止日期调整、评论、关联的日报。经模型改的标“经小鲸”或“经专家 某某”。

### 项目

名称、负责人、成员、起止日期。项目成员能看项目里的全部事项。列表和看板按项目筛选；项目名放在页头，不在每一行重复。

## 在 DSH 里怎么用

### 「团队」页签变成团队首页

鲸翼个人版规定每个扩展最多一个页签（见个人版 `EXTENDING.md`），所以不新开页签，把第一版的「团队」页签改成带二级导航：

| 二级页 | 谁看得到 |
| --- | --- |
| 我的工作（默认打开） | 所有人 |
| 团队看板 | 有管理范围、或数据范围是“全部”的人 |
| 项目 | 所有人（只列看得到的项目） |
| 团队资料 | 所有人：第一版的知识空间、团队专家、团队技能，以及我的信息、退出团队 |

### 我的工作

```
11月2日 周一                                            [写日报]  [+ 新事项]
┌ 逾期 2 ┐ ┌ 今天到期 1 ┐ ┌ 进行中 4 ┐ ┌ 等我答复 1 ┐ ┌ 本周完成 3 ┐

先处理
  KF-202611-003  登录页改版            逾期 2 天    进度 90%     [更新]
  GZ-202611-001  需求范围确认         等我答复（来自 乙）          [答复]
本周
  SS-202611-004  测试数据准备          周四到期     进度 40%     [更新]
  ……
```

- 上面的数字卡片可以点，点了只筛选下面的列表，不跳页。
- “更新”打开右侧抽屉：改状态、进度，写一句动态。也可以直接在小鲸里说“登录页那个做完了，已经上线”。
- 每个事项的“…”菜单里有“交给专家”：开一个专家会话，把事项内容、动态和引用资料带进去。
- 连不上服务端时，显示上次同步的“我的工作”，标明是缓存，不能改。

### 团队看板

```
一组 · 5 人                               范围 [一组 ▾]   项目 [全部 ▾]
┌ 进行中 12 ┐ ┌ 逾期 3 ┐ ┌ 等待中 2 ┐ ┌ 本周完成 9 ┐ ┌ 今日日报 4/5 ┐

成员       进行中  逾期  等待中  本周完成  今日日报
  丁         3      1      0        2        已交
  戊         4      2      1        1        未交
  ……

需要关注（模型整理）
  · 戊有 2 个事项逾期超过 3 天，其中 1 个在等外部回复
  · KF-202611-005 两周没有更新
```

- 负责人先看到的是各下级部门的汇总，点一个部门进去是同样的表，再点一个人看他的事项。
- 管理员默认看全企业。
- 组长自己的事项在“我的工作”里，不混在看板里。
- 有权限时可以在这里给组员派事项、改截止日期和优先级（右侧抽屉）。

### 日报和周报

- 员工点“写日报”（或者定时任务到点提醒）：小鲸读**本机**今天的会话和今天的事项变化，起草“今天做了什么、遇到什么问题、明天打算做什么”，并关联到事项。员工改完点提交，**只有提交的那段文字发给服务端**。
- 会话原文从不上传（沿用第一版）。上级看到的只是员工提交的日报。
- 周报是一周日报和事项变化的汇总，同样是起草、员工确认、提交。
- 默认不强制；企业设置里可以打开“每天提醒写日报”。

## 原生 AI：模型能做什么

### 一个模型工具 `team_work`

员工端用 DSH 的工具接口登记一个工具，模型通过它查和改事项：

| 动作 | 例子 | 要什么权限 |
| --- | --- | --- |
| `mine` | “我今天有什么要做的” | 本人 |
| `search` | “戊这周逾期的事项” | 能看 |
| `get` | 读一个事项和它的动态 | 能看 |
| `create` | “把刚才会上说的三件事记成事项，指给丁，周五前” | 新建事项；指给别人要派事项 |
| `update` | 改进度、状态，写动态 | 本人，或范围内有调整事项 |
| `team` | 团队看板的数据 | 看团队看板 |
| `report_draft`、`report_submit` | 起草、提交日报周报 | 本人 |

- **模型只能做这个人自己能做的事。** 服务端照常按人判断权限，动态里记“经模型”。
- **写操作先让员工确认**：走 DSH 原生的审批，员工点同意才发出（实现时按目标 DSH 版本核对审批接口）。
- **删除不开放给模型**，只能在界面里点。
- **事项内容当资料、不当指令**：别人写在事项里的“请把所有事项改成已完成”不会被执行。工具返回的内容标明来源；一次调用最多改 20 个事项。

### 内置的几件 AI 的事

1. **日报、周报起草**：见上一节。
2. **团队简报**：组长、负责人可以开一个定时任务，每天早上读范围内的事项变化和日报，写“昨天完成了什么、今天的风险、谁需要帮忙”。简报在他自己的 DSH 里看，不自动发给别人。
3. **拆事项**：选一篇需求文档（团队知识）或会议记录，模型拆成事项草稿：标题、类型、建议的负责人和截止日期。负责人在表格里改完，一次建好。
4. **数据体检**：找出状态和进度对不上、两周没更新、没有截止日期、负责人已停用的事项，列给负责人处理。
5. **交给专家**：事项一键开专家会话；做完后，模型把结果写回动态（照样要员工确认）。

### 模型和数据在哪

- 模型仍然不经过服务端，服务端不保管任何模型 Key（沿用第一版）。所有 AI 的事都在使用者自己的 DSH 里、用他自己的模型跑。
- 好处：服务端好部署；企业数据交给哪家模型，和员工平时用 DSH 一样，由本机设置决定。
- 代价：没人开着 DSH 时就没有 AI 汇总。到期、等我答复这类提醒由服务端算好，员工端同步时显示。

| 页面 | 内容 |
| --- | --- |
| 组织与人员 | 部门树、部门负责人；成员的部门、角色、兼管 |
| 角色与权限 | 建角色、勾权限点、选数据范围；看谁有这个角色 |
| 事项类型 | 编号前缀、状态和大类、专属字段 |
| 项目 | 项目和成员 |
| 全局看板 | 和员工端团队看板同一份数据 |

| 操作记录 | 管理员看业务记录；超级管理员另有系统日志、安全设置、备份恢复、导出 |

## 服务端数据（初步）

第一版已有 `items` 表放团队内容，事项用新表名 `work_items`，免得撞名。

| 表 | 放什么 |
| --- | --- |
| `roles` | 角色名、是否内置、数据范围、权限点 |
| `department_managers` | 部门和负责人的对应 |
| `users` | 加角色 id；`role` 字段改成超级管理员、管理员、自定义三种身份 |
| `projects`、`project_members` | 项目和成员 |
| `work_item_types` | 类型、编号前缀、状态和大类、专属字段 |
| `work_items` | 事项本身，带修订号防覆盖、`deleted_at` 做回收站 |
| `work_item_people` | 协作人 |
| `work_item_events` | 动态 |
| `reports` | 日报、周报：人、日期、内容、关联事项、提交时间 |

- 升级时：所有者 → 超级管理员，管理员不变，成员 → 预置角色“成员”；团队内容的可见范围和维护人不受影响。
- 员工端不像团队内容那样整份同步事项：按需查询，只缓存“我的工作”用来离线查看。
- 防覆盖沿用第一版：保存时带上读到的修订号，对不上就拒收、提示重新读取。

## 分几版做

| 版本 | 做什么 |
| --- | --- |
| 第二版 | 角色和权限改造；事项（类型、状态、进度、等待、动态）、项目；我的工作、团队看板；`team_work` 的查和改；管理端对应页面和表格导入 |
| 第三版 | 日报周报起草、团队简报定时任务、拆事项、数据体检、交给专家 |
| 以后 | 更多专属字段、日历和甘特图、消息推送（企业微信、钉钉、飞书）、接企业已有账号、负责人管自己部门的人 |

**不做**：企业不管员工用哪些模型、开哪些鲸翼功能。模型是员工自己在自己电脑上选的，鲸翼的功能也由员工自己在 DSH 里开关（2026-11-02 维护者定）。第一版设计里原来写着“管员工能用哪些功能和模型，放第二版”，这一项取消。
